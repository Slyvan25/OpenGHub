# Publishing on Flathub

Every release already carries a Flatpak bundle (`OpenGHub_<version>.flatpak`) that anyone can
install with `flatpak install --user OpenGHub_*.flatpak`. Flathub is the next step: it puts
OpenGHub in GNOME Software and KDE Discover and gives `flatpak install flathub
io.github.slyvan25.OpenGHub`.

Everything needed is generated by the release workflow; submitting is a pull request.

## What the app id has to be

Flathub only accepts ids under a domain you own, or `io.github.<user>.<repo>` for a GitHub
project. Ours is **`io.github.slyvan25.OpenGHub`** — matching `github.com/Slyvan25/OpenGHub`,
user lowercased, repository name as it is written. It is set in `src-tauri/tauri.conf.json`,
`src-tauri/src/sandbox.rs` and the two files in `packaging/flatpak/`.

## Submitting

1. **Tag a release** and let the workflow finish. It attaches
   `flathub-manifest-<version>.tar.gz`, which holds exactly the two files Flathub wants:
   `io.github.slyvan25.OpenGHub.yml` (the .deb by URL and sha256, with `x-checker-data` so
   Flathub's bot proposes later versions by itself) and
   `io.github.slyvan25.OpenGHub.metainfo.xml`.

2. **Fork [flathub/flathub](https://github.com/flathub/flathub)** and branch from `new-pr`,
   *not* from `master`:

   ```sh
   git clone git@github.com:<you>/flathub.git && cd flathub
   git checkout -b openghub origin/new-pr
   tar -xzf ~/Downloads/flathub-manifest-0.1.1.tar.gz
   git add io.github.slyvan25.OpenGHub.yml io.github.slyvan25.OpenGHub.metainfo.xml
   git commit -m "Add io.github.slyvan25.OpenGHub"
   git push -u origin openghub
   ```

3. **Open a pull request against `new-pr`.** A bot builds the manifest and comments with the
   result; a reviewer then reads it. Test the same build locally first:

   ```sh
   flatpak install -y flathub org.gnome.Platform//47 org.gnome.Sdk//47
   flatpak-builder --user --install --force-clean build-dir io.github.slyvan25.OpenGHub.yml
   flatpak run io.github.slyvan25.OpenGHub
   ```

4. **Answer the two questions that always come up.** Both are in the manifest's comments, but
   say it in the PR as well:

   - **`--device=all`** — OpenGHub is a device-configuration tool. It speaks HID++ over
     `/dev/hidraw*` and creates the force-feedback wheel and virtual keyboard on `/dev/uinput`.
     Neither has a portal, and `--device=input` does not cover `hidraw`.
   - **`--talk-name=org.freedesktop.Flatpak`** — helpers that must run on the host:
     `pkexec` (installs the udev rule, with the desktop's own password dialog), `gst-launch-1.0`
     and `parec` (the screen sampler and audio visualizer), `steam` / `lutris` / `xdg-open` (the
     Games tab), `loginctl` (the "lock computer" action). The app never runs anything else on
     the host; `src-tauri/src/sandbox.rs` is the single place this goes through.

   Reviewers may ask for a build **from source** instead of repackaging the .deb. That means
   vendoring the dependencies for an offline build — `flatpak-cargo-generator.py` over
   `src-tauri/Cargo.lock` and `flatpak-node-generator npm package-lock.json` — and building with
   the Rust and Node SDK extensions. It is more machinery to keep current; starting from the
   .deb (the same binary the other packages ship) is usually accepted.

5. **After the merge** you get `flathub/io.github.slyvan25.OpenGHub`, where you are maintainer.
   Later versions need nothing: the update bot opens a PR when a new GitHub release appears,
   thanks to `x-checker-data`. Merge it and Flathub builds.

6. **Verify the app** at [flathub.org/apps/io.github.slyvan25.OpenGHub](https://flathub.org/apps/io.github.slyvan25.OpenGHub)
   → *Verify*. For a `io.github.*` id it asks you to push a token to the repository, which
   proves ownership and gives the listing its verified badge.

## Keeping the metainfo honest

`packaging/flatpak/io.github.slyvan25.OpenGHub.metainfo.xml` is what stores display: summary,
description, screenshots (served from `docs/screenshots/` on the default branch) and the release
list. `appstreamcli validate` runs on it in CI. When you add a release, the workflow rewrites
the `<release>` entry for the tagged version; anything else — a new screenshot, a better
summary — is a normal edit here and reaches Flathub with the next update PR.
